## 1. ANALYSE DES 5 BUGS P0

### 🐛 Bug #1 : Modèle 3D WRAITH forcé (coerceAvatarId)

| Champ | Valeur |
|-------|--------|
| **Fichier** | `src/rpg/characters/playerAvatars.ts:121-124` |
| **Sévérité** | 🔴 P0 — bloque la diversité visuelle des personnages |
| **Impact** | Tout avatar non reconnu → forcé sur `DEFAULT_AVATAR = "wraith"`. Les joueurs voient Wraith au lieu de leur personnage. |
| **Cause racine** | `coerceAvatarId()` est un garde-fou anti-404 légitime (avatars retirés : Rampage, Trooper) mais il est trop agressif : il ne distingue pas un id retiré d'un id valide dont le GLB a échoué à charger (timeout réseau, asset manquant sur disque, corruption). |
| **Flux** | `App.tsx:248` → `coerceAvatarId(appearance.model)` → si id absent de `PLAYER_AVATARS` → `"wraith"`. Aucune journalisation du fallback, aucun mécanisme de retry. |

**Plan d'action** :
1. Ajouter un **log warning** dans `coerceAvatarId()` quand le fallback est déclenché (id original, raison)
2. Ajouter un **mécanisme de retry** dans la chaîne de chargement du modèle avec exponentielles (3 tentatives, 1s/2s/4s)
3. Créer un **fallback model visuellement distinct** (un placeholder gris/silhouette) au lieu de forcer Wraith silencieusement
4. Ajouter un **test unitaire** qui vérifie que les ids valides du roster ne sont jamais coercés

### 🐛 Bug #3 : SSAO NormalPass manquant

| Champ | Valeur |
|-------|--------|
| **Fichier** | `src/rpg/runtime/postfx/PostProcessingPipeline.tsx:48-61` |
| **Sévérité** | 🟠 P0 — erreur runtime silencieuse, qualité visuelle dégradée |
| **Impact** | Le composant `<SSAO>` de `@react-three/postprocessing` nécessite un `NormalPass` pour fonctionner. Sans lui, soit l'effet est invisible (rendu incorrect), soit il lance une erreur console. |
| **Cause racine** | Le pipeline rendu définit SSAO sans `<NormalPass>` préalable. Les versions récentes de `postprocessing` exigent ce pass pour calculer les normales en espace écran. |
| **Quick fix** | 2 options : (A) ajouter `<NormalPass>` avant `<SSAO>`, ou (B) wrapper dans un `React.Suspense` avec fallback silencieux. |

**Plan d'action** :
1. Ajouter `import { NormalPass } from "@react-three/postprocessing"` (vérifier si l'import existe)
2. Insérer `<NormalPass />` juste avant la balise `<SSAO>` dans le bloc conditionnel `{ssao && (`
3. Si `NormalPass` n'est pas exporté par la version actuelle, utiliser `useNormalPass()` de `postprocessing` directement OU wrapper try-catch autour du SSAO
4. Vérifier que le SSAO est effectivement visible après le fix (capture d'écran before/after)
5. Ajouter un **test de rendu** : `expect(PostProcessingPipeline).toContainNormalPass()`

### 🐛 Bug #5 : DB connection failed en mode navigateur

| Champ | Valeur |
|-------|--------|
| **Fichier** | `electron/database.ts:65-99`, `src/utils/storage.ts:25-42` |
| **Sévérité** | 🟡 Medium — fonctionnel (fallback localStorage), mais pas de persistance serveur |
| **Impact** | MySQL uniquement accessible via `window.narvosLauncher.mysqlQuery` (pont IPC Electron). En mode navigateur pur, le pont n'existe pas → fallback localStorage. |
| **Cause racine** | C'est un **choix d'architecture**, pas un bug. Le backend MySQL + WebSocket partagent le même problème : pas de serveur central. |
| **Note** | Ce bug est **couplé au Bug #2** (WebSocket). Résoudre le serveur backend résout les deux. |

**Plan d'action** :
1. Même plan que Bug #2 — le démarrage du serveur backend active à la fois WS et DB
2. Ajouter un **endpoint REST** ou **WS handler** `DB_QUERY` pour que le client navigateur puisse interroger la DB via le serveur (pas seulement via Electron IPC)
3. Vérifier que `dbStore.ts` détecte correctement le mode (Electron vs navigateur) et choisit le bon pont
